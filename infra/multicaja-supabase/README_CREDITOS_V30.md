# NAVARRO 360 V30.1 — Créditos compartidos (preparación)
**No activo.** Se prepara una migración independiente sobre la base Supabase ya prevista. El repositorio no contiene ninguna información de clientes real, ni credenciales. La versión local 29.9.3 sigue operativa.

## Activación
1. Conectar/autorizar un proyecto Supabase del comercio. Confirmar proyecto, usuarios Auth individuales y asignaciones a las cajas COMPUTADORA, PABLO, DIANA y GOLI. Deshabilitar auto-registro público. Configurar un administrador; para registrar movimientos también necesita asignación a caja.
2. Ejecutar 001 (corregida delimitación de la función is_active) y 002 en un proyecto de pruebas. No publicar claves secretas.
3. Probar autorización y concurrencia con dos sesiones reales: anónimo denegado; vendedor de caja activa lee expedientes compartidos; identidad de caja tomada del servidor; vendedor desactivado denegado; roles y ventas generales conservan separación de 001; dos abonos simultáneos no pueden exceder saldo; repetir folio no duplica; mismo folio con otros datos se rechaza; reimpresiones no envían crédito.
4. Integrar el cliente web en modo de prueba usando la clave publicable y sesión Auth. Las dos RPC son nv360_credit_customer_create y nv360_credit_append. No añadir una segunda venta al panel al registrar abono. Leer los dos conjuntos paginados; saldo = ventas menos abonos; abonos por fecha de negocio (America/Mexico_City) y box_code para arqueo; administrador agrega todas las cajas. No usar saldos de caché para autorizar abonos. Si no hay red, mostrar saldo no verificado y bloquear confirmación de abono.
5. Migración: exportar respaldo de créditos desde cada uno de los cuatro dispositivos. Conservar sus UUID de cliente y folios de venta/abono. Revisar homónimos y duplicados con el propietario antes de unificar clientes; no unir automáticamente. Importar clientes primero, ventas después, abonos al final con p_legacy_at original; validar saldos y origen. Cada caja importa sus propios registros con su sesión; no borrar local hasta comparar y confirmar los recibos. La fecha received_at distingue importación de fecha del movimiento original.
6. Activar cliente web solo después de verificar pruebas, comparar saldos y completar respaldo de las cuatro cajas. Incorporar panel móvil existente mediante acceso privado al mismo servidor. Sin conexión, los abonos no se aceptan; ventas a crédito requieren cola idempotente persistente del ticket finalizado, con indicador de pendiente. El flujo de impresión, presupuesto, cobro normal y stock permanece intacto.
